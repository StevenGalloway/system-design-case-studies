# Data Platform and Analytics Infrastructure

## Purpose

The Data Platform provides the foundational infrastructure for real-time and batch analytics, personalization signal processing, operational intelligence, and business metrics across all Netflix services.

This domain bridges the gap between raw event streams generated by hundreds of millions of devices and the model features, dashboards, alerting pipelines, and business reports that the rest of the organization depends on. Without reliable data infrastructure, every downstream system degrades: personalization goes stale, anomaly detection goes blind, and business decisions lose their empirical foundation.

---

## Core Subsystems

| Subsystem | Technology | Purpose |
|-----------|-----------|---------|
| Event Streaming | Apache Kafka | Durable, ordered event bus for all platform telemetry and domain events |
| Stream Processing | Apache Flink | Stateful, exactly-once streaming transformations and real-time feature computation |
| Batch Processing | Apache Spark | Large-scale historical data processing, ML training datasets, and analytical aggregations |
| Lakehouse Table Format | Apache Iceberg | ACID-compliant table format with schema evolution, time-travel, and partition pruning |
| Online Feature Store | Custom low-latency store | Sub-10ms feature serving for real-time ML inference |
| Offline Feature Store | Iceberg + Spark | Training data materialization and batch feature backfills |
| Metadata Catalog | Internal data catalog | Data lineage, ownership, schema registry, and discovery |

## Key Design Decisions

| Decision | Rationale |
|---------|-----------|
| Dual-speed pipeline (streaming + batch) | Real-time use cases (recommendations, alerting) require seconds-fresh data; analytical use cases (reporting, training) tolerate minutes-to-hours latency |
| Iceberg as the lakehouse table format | Provides ACID transactions, schema evolution without full rewrites, hidden partitioning, and time-travel queries for debugging and compliance |
| Data mesh ownership model | Domain teams own their data products end-to-end, including schema contracts, SLAs, and quality monitoring; central platform provides infrastructure |
| Exactly-once semantics | Flink's transactional output combined with Iceberg ACID writes prevents duplicate records in downstream stores, which is critical for billing and engagement metrics |

---

## Pros / Cons

### Pros
- Serves both millisecond-latency real-time feature reads and petabyte-scale historical analytics from a unified architecture
- Strong data governance: every dataset has an owner, a schema contract, and a freshness SLA
- Decoupled producers and consumers via Kafka; teams can evolve schemas without coordination windows

### Cons
- Operational complexity of running three distinct compute frameworks (Kafka, Flink, Spark) with different operational models
- Schema management across distributed producers requires discipline; schema registry enforcement must be actively maintained
- Exactly-once processing adds state management overhead and increases checkpoint storage costs

## Failure Modes and Mitigation

| Failure | Impact | Mitigation |
|---------|--------|-----------|
| Kafka broker failure | Event ingestion disruption | Replication factor >= 3; auto-leader election; broker auto-restart |
| Kafka consumer lag | Stale features; delayed alerting | Consumer auto-scaling; lag alerting; dedicated lag-recovery consumer groups |
| Flink job failure | Stream processing gap | Checkpointed state recovery; automatic job restart with backpressure handling |
| Spark job failure | Batch pipeline gap | Idempotent output writes to Iceberg; retry with incremental processing from last committed offset |
| Feature staleness | ML model serving with stale inputs | Freshness SLA monitoring; alerting on stale partitions; fallback to population defaults |
| Data corruption | Downstream model and analytics errors | Iceberg ACID guarantees; checksum validation at ingest; schema enforcement at the Kafka schema registry |

## Service Level Objectives

| Metric | Target | Window |
|--------|--------|--------|
| End-to-end event delivery latency (p99) | <= 5 seconds | 24-hour rolling |
| Batch pipeline freshness (analytical tables) | <= 15 minutes | Daily measurement |
| Online feature store serving latency (p99) | <= 10 ms | 30-day rolling |
| Platform availability (Kafka + Flink) | >= 99.9% | 30-day rolling |
| Data completeness (events processed / events produced) | >= 99.99% | 24-hour rolling |
| Schema contract violation rate | 0% | Continuous enforcement |

## Security Considerations

- Data classification enforced at the topic and table level: PII data access requires explicit role binding
- PII tokenization before persistence: user IDs and device identifiers are pseudonymized at the ingest layer
- Column-level access control on Iceberg tables for sensitive signals (location, payment-adjacent data)
- All data in transit encrypted via TLS; all data at rest encrypted with key rotation on a 90-day cycle
- Audit logging for all data access to sensitive tables, retained for 365 days
